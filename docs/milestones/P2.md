# Product P2 Specification and Implementation Roadmap

**Status:** Approved Specification & Implementation Roadmap (P0 and P1 complete baselines; P2 ready for implementation)  
**Document Version:** 1.0  
**Baseline:** Product P0 and P1 Accepted Baselines (410 Python unit/integration tests passing; Playwright acceptance passing)  
**Target Release:** ArmStride Product P2 ("Debugger and Input Expansion")  

---

## 1. Executive Summary and Product Baseline

### 1.1 Baseline Acceptance
Product P0 and Product P1 are complete, verified, and accepted as the stable baseline. All 410 automated tests (unit, simulation, integration, frontend, and Playwright workflows) pass and represent an immutable regression test floor.

The accepted baseline guarantees:
- ARMv7-A little-endian architecture profile executing on pinned Unicorn 2.1.4.
- Mixed ARM/Thumb code listings and data regions (`$a`, `$t`, `$d` mapping symbols).
- Runtime ARM/Thumb interworking via native CPSR T-bit resolution (`BX`, `BLX`, `POP {pc}`, `LDM {pc}`).
- Thumb-2 IT block execution (`IT`, `ITT`, `ITE`) with step-by-step ITSTATE preservation and skip reporting (`executed: false`).
- Strictly atomic `step()` execution with snapshot rollback on faults.
- Pre-execution breakpoints with single-step resume bypass.
- Bounded `run()` loop composing atomic steps with non-blocking concurrent `stop()` signaling.
- Strict logical memory model: known instructions, non-executable data regions, synthetic scratch stack, and unmapped `??` bytes.
- User Baseline State isolation with non-destructive `reset()`.
- Synchronous local HTTP REST API and responsive Svelte 5 frontend.

### 1.2 Product P2 Objectives: "Debugger and Input Expansion"
Product P2 deepens the existing ARM debugger and broadens input ingestion without compromising its fundamental execution model or logical memory semantics.

Product P2 encompasses five core feature groups:
1. **Direct ARM ELF Loading:** Load statically linked 32-bit little-endian ARM ELF executables (`ET_EXEC`) as a third `ProgramImage` producer. Position-independent executables (`ET_DYN` / PIE) are deferred post-P2.
2. **ELF Symbol Support:** Extract and index function and object symbols into decoupled `ProgramMetadata` for UI navigation, PC labels, and breakpoint targeting.
3. **DWARF Address/Source-Line Mapping:** Extract `.debug_line` mappings to correlate instruction addresses with `file:line` locations without fabricating source files.
4. **Memory Watchpoints:** Add memory access monitoring (`read`, `write`, `read_write`) with post-instruction committed-boundary evaluation and dual observability on Step and Run.
5. **Bounded Step Back / Execution History:** Provide state rewinding for up to 100 historical steps via a linear journal with lazy memory capture, preserving `step_seq` invariance, introducing `state_revision`, and isolating User Baseline State.

In parallel, a non-blocking research track (**P2-R**) evaluates Cortex-M microcontroller simulation feasibility in an isolated spike.

### 1.3 Explicit Non-Goals and Out-of-Scope Capabilities
To maintain architectural boundaries, the following are strictly excluded from Product P2:
- **Cortex-M Production Commitment:** Cortex-M is not part of the P2 release commitment; it is addressed purely through the non-blocking `P2-R` research gate.
- **MMIO Peripheral Emulation:** Watchpoints are passive debugger observation hooks. Peripheral simulation (read/write callbacks, side-effects, device registers, interrupts, timers) is deferred across 5 distinct layers post-P2.
- **Full DWARF Debugger:** No variable inspection, expression evaluation, lexical scopes, type reconstruction, or DWARF CFI stack unwinding.
- **Host Filesystem Source Browsing:** DWARF line mappings display metadata strings (e.g. `main.c:42`); ArmStride will not read or render host source files.
- **Position-Independent Executables (`ET_DYN` / PIE):** Deferred post-P2 until load-bias and dynamic relocation semantics are designed.
- **Relocatable Object Linking (`ET_REL`):** ArmStride is not a linker; unlinked `.o` files are rejected with an actionable diagnostic.
- **Dynamic Linking / Shared Libraries (`PT_INTERP`):** Dynamic loaders and shared objects (`.so`) are rejected.
- **Branching Time-Travel Trees:** Step Back is strictly linear. Branching execution purges forward history; no persistent alternate history branches.
- **Non-ARM ISAs:** RISC-V, AArch64, x86, and MIPS remain future milestone candidates.
- **Floating Point / SIMD:** VFP and NEON instructions remain excluded from the execution profile.

## 2. Product P2 Feature Group Specifications

### 2.1 Feature Group 1: Direct ARM ELF Loading

#### 2.1.1 Third Producer Architecture (ADR-019)
The ELF loader acts as a third producer feeding the existing core:

```text
Assembly Source ───────┐
                      │
Disassembly Import ────┼──> ProgramImage ──> SimulationSession.load
                      │
P2 ELF Loader ─────────┘        +
                                ProgramMetadata (Symbols + DWARF Lines)
```

The ELF path creates **zero parallel execution machinery**:
- No `ElfSimulationSession`
- No `ElfExecutionBackend`
- No `ElfMachineState`

Code and data loaded from an ELF binary execute through the exact same `ProgramImage`, `MemoryState`, `UnicornBackend`, atomic `step()`, and rollback mechanisms as existing inputs.

#### 2.1.2 Supported ELF Subset
The loader validates the ELF header strictly:
- **ELF Class:** 32-bit (`ELFCLASS32`). 64-bit (`ELFCLASS64`) rejected with `unsupported_elf_class`.
- **Endianness:** Little-endian (`ELFDATA2LSB`). Big-endian (`ELFDATA2MSB`) rejected with `unsupported_elf_type`.
- **Machine Architecture:** ARM (`EM_ARM` / 0x28). Others rejected with `unsupported_elf_machine`.
- **ELF Type:** Strictly `ET_EXEC` (executable). Position-independent executables (`ET_DYN` / PIE) are deferred post-P2 and rejected with `elf_pie_unsupported` (absence of `PT_INTERP` does not prove `ET_DYN` needs no runtime relocation). Relocatable objects (`ET_REL`) rejected with `elf_relocation_unsupported`.
- **Dynamic Linking:** Segments of type `PT_INTERP` or dynamic relocations are rejected with `elf_dynamic_linking_unsupported`.

#### 2.1.3 Segment Mapping and Logical Memory Semantics (ADR-025)
- **Mapping Symbols Partitioning:** `PT_LOAD` defines memory placement and permissions (`PF_R`, `PF_W`, `PF_X`). Executable segments (`PF_X`) are partitioned using ARM ELF mapping symbols (`$a` for ARM, `$t` for Thumb, and `$d` for inline data/literal pools), reusing the mixed ARM/Thumb/Data `ProgramImage` model from P1.
- **Inline Literal Pools as Data:** Any `$d` ranges inside executable segments remain non-executable `DataRegion`s mapped into known memory. Branching into them halts with `non_executable_target`.
- **Fail-Closed on Ambiguous Regions:** Mixed executable regions lacking reliable mapping symbols fail closed with actionable diagnostic `ambiguous_elf_execution_mode`.
- **Data Segments:** Segments with `PT_LOAD` and `PF_R` or `PF_W` without `PF_X` become `DataRegion` records (known, non-executable memory).
- **BSS Zero Expansion:** Where `p_memsz > p_filesz`, the trailing interval `[p_vaddr + p_filesz, p_vaddr + p_memsz)` is initialized to explicit known zeros as a `DataRegion`. Page-padding bytes outside `p_memsz` remain strictly unknown memory.
- **Permissions:** Segments without `PF_W` are marked read-only; segments with `PF_W` are marked writable.

#### 2.1.4 Entry Point and Initial Mode
- The initial PC is taken from `e_entry`.
- If `e_entry & 1 == 1`, initial mode is `thumb` and entry PC is canonicalized to `e_entry & ~1`.
- If `e_entry & 1 == 0`, initial mode is `arm` and entry PC is `e_entry`.
- Address `0x00000000` is NOT inherently invalid; validate it against the loaded executable image (valid if an executable instruction is mapped there).
- The canonical entry PC must match a valid decoded instruction start in `ProgramImage`.

#### 2.1.5 Independent Resource Bounds (ADR-025)
- All executable `PT_LOAD` segments are decoded eagerly during load subject to independent limits:
  - Raw ELF input file size <= 10 MiB.
  - Decoded instruction count <= 10,000 instructions.
  - Total logical loaded memory (including BSS) <= 16 MiB.
  - Backing-page allocation <= 64 MiB (reusing MemoryState page budget).
  - ELF segment count <= 32 segments, section count <= 128 sections.
- Exceeding any bound immediately rejects the file with an actionable diagnostic (`elf_resource_limit_exceeded`). Speculative lazy disassembly is avoided.

### 2.2 Feature Group 2: ProgramMetadata, Symbols, and DWARF Lines

#### 2.2.1 Decoupled Metadata Architecture (ADR-020)
Execution domain models (`ProgramImage`, `Instruction`, `DataRegion`) remain decoupled from debug metadata:

```text
SimulationSession
├── ProgramImage (Authoritative Execution Truth)
│   ├── instructions: Sequence[Instruction]
│   ├── data_regions: Sequence[DataRegion]
│   └── execution_locations: dict[(address, mode), Instruction]
└── ProgramMetadata (Decoupled Auxiliary Metadata)
    ├── symbols: SymbolTable
    └── lines: LineTable
```

Native `pyelftools` objects are strictly confined to `src/armstride/elf/` and never leak into `SimulationSession`, HTTP schemas, or frontend state.

#### 2.2.2 Symbol Support
- Extracted from `.symtab` and `.dynsym`.
- Collects function symbols (`STT_FUNC`), data objects (`STT_OBJECT`), and section labels.
- Indexed by address (`by_address: dict[int, list[SymbolEntry]]`) and by name (`by_name: dict[str, SymbolEntry]`).
- Stripped ELFs without symbols load and execute normally with empty symbol metadata.

#### 2.2.3 DWARF Address/Source-Line Mapping
- Extracted from `.debug_line` table into `LineTable`.
- Maps instruction addresses to `(file_path, line_number, column)`.
- **Missing Source Display:** If the source file is not present, the UI displays `file_path:line_number` without attempting host filesystem reads or syntax rendering.
- Absence or corruption of DWARF sections generates non-fatal diagnostics and does not prevent execution.

### 2.3 Feature Group 3: Memory Watchpoints

#### 2.3.1 Watchpoint Model
A Watchpoint monitors logical memory access over a specified range:
- `address`: 32-bit starting address.
- `length`: Range length in bytes (1 to 4096 bytes).
- `kind`: `read`, `write`, or `read_write`.
- Capacity: Up to 32 concurrent watchpoints per session.

#### 2.3.2 Post-Instruction Committed-Boundary Semantics & Dual Observability (ADR-021)
Breakpoints and Watchpoints have fundamentally different timing:
- **Breakpoint:** Evaluated *before* instruction execution; stops before the instruction runs.
- **Watchpoint:** Discovered through memory accesses performed *during* instruction execution and evaluated at the committed Step boundary.

Dual observability and evaluation rules:
1. One atomic `step()` executes and commits its architectural effects successfully.
2. Committed memory events (`memory_reads`, `memory_writes`) are compared against active watchpoints.
3. An access intersecting `[wp.address, wp.address + wp.length)` triggers a hit.
4. **Observable on Step:** Single Step reports committed `watchpoint_hits` in `StepResult`, while remaining paused.
5. **Observable on Run:** If committed watchpoint hits occur during a `run()` loop, Run terminates immediately with `stop_reason = "watchpoint"`.
6. **Multi-Access Ordered Hits:** Instructions with multiple memory transfers (e.g. `LDM`, `STM`) preserve ordered multiple hits from that single instruction.
7. **Same-Value Writes:** A write instruction that writes the exact same value already in memory (`before == after`) is an architectural CPU write and **must trigger** write watchpoints.
8. **Failed Step Isolation:** If an instruction faults (unmapped memory, unaligned access, etc.), the transaction rolls back. Attempted accesses in a failed step **never** trigger watchpoints.
9. **Never Rollback:** A successful instruction is **never rolled back** because it triggered a watchpoint. Machine state remains at a valid architectural Step boundary.

#### 2.3.3 Separation of Execution Stop State from Debugger Observations
A Step may simultaneously produce an architectural stop condition such as `pc_not_loaded` and one or more Watchpoint hits.
- Neither fact is discarded: `RunResult.stop_reason` is `"watchpoint"`, and `RunResult.last_step.stop_condition` retains `"pc_not_loaded"`.
- **Deterministic Stop Precedence Matrix:**
  1. *Pre-execution Breakpoint:* Run stops before instruction execution; no memory access occurs, so no watchpoint can hit.
  2. *Execution Fault:* Unmapped access, illegal instruction -> atomic rollback; no watchpoint hits; Run stops with fault reason.
  3. *Post-execution Watchpoint Hit:* Instruction commits; Run stops with `"watchpoint"`; architectural stop preserved in `last_step_result`.
  4. *Post-execution Architectural Stop:* `pc_not_loaded` halts Run if no watchpoint was hit.
  5. *User Stop:* `POST /api/sessions/{id}/stop` signals clean stop between Steps.
  6. *Run Bounds:* `step_limit` or `time_limit`.

#### 2.3.4 Decoupling from MMIO (ADR-024)
Watchpoints are passive observation hooks. They do not simulate peripheral behavior, trigger callbacks, mutate data, or advance device timers. MMIO peripheral simulation is deferred post-P2 across 5 explicit layers:
1. `Named Memory Metadata`
2. `Memory Access Callbacks`
3. `Passive Peripheral Registers`
4. `Active Peripheral State Engines`
5. `System-Level Interrupt/Clock Simulation`

### 2.4 Feature Group 4: Bounded Step Back / Execution History

#### 2.4.1 Bounded Linear History Journal with Lazy Memory Capture
`SimulationSession` maintains an `ExecutionHistoryJournal` holding up to 100 historical steps in a FIFO ring/deque.

Prior to committing each successful atomic Step, a snapshot of the pre-step state is pushed to the journal:
- General registers R0–R15, CPSR, PC, and execution mode at the step boundary.
- Pre-step original memory bytes captured lazily from the step's committed write events / write hooks.
- For multiple writes to the same byte within one instruction, retain the pre-Step original byte once (the first pre-value observed) for exact reverse restoration.
- Previous `last_step` result and current `step_seq`.

#### 2.4.2 Monotonic `step_seq` Invariance and `state_revision` (ADR-022)
- `step_seq` counts committed architectural forward Steps only.
- Step Back must **NOT increment or decrement `step_seq`**.
- After stepping backward, a newly committed forward Step continues from the existing monotonic maximum (`max_step_seq + 1`), not the historical restored value.
- A separate `state_revision` integer counter tracks all state mutations (Step, Step Back, edit, Reset, Load) monotonically for reliable client cache and UI resynchronization.

#### 2.4.3 User Baseline State Isolation
Step Back restores **Runtime State ONLY**.
- `UserBaselineState` is never mutated by CPU execution or Step Back.
- A subsequent `reset()` cleanly restores state from the intact User Baseline.

#### 2.4.4 Linear History & Invalidation Rules
- **Linear Forward Purge:** If the user steps or runs forward after stepping back, all forward history entries beyond the rewind point are discarded (no branching time-travel trees).
- **Manual Edit Invalidation:** Any manual state edit (register edit, memory patch, PC modification) invalidates and clears the entire history journal.
- **Reset and Load Invalidation:** Session Reset and replacement program Load clear the entire history journal.

## 3. Non-Blocking Research Track: Cortex-M Feasibility Spike (P2-R)

Cortex-M simulation is an important candidate for future milestones but is explicitly decoupled from the Product P2 release commitment (ADR-023).

An isolated research spike in `spikes/p2_cortex_m/` probes Unicorn's Cortex-M capabilities:

| Probe | Test structure | Required observation / completion condition |
| --- | --- | --- |
| CM-01: CPU Model Availability | Initialize Unicorn with `UC_CPU_ARM_CORTEX_M3` / `UC_CPU_ARM_CORTEX_M4` | Confirm Unicorn supports M-profile models in Thumb mode. |
| CM-02: Vector Table & Reset Entry | Load vector table at `0x00000000` (`Initial SP`, `Reset Handler PC`) | Verify whether Unicorn natively loads SP and PC from vector table or requires manual setup. |
| CM-03: Dual Stack Pointers | Inspect and mutate `MSP` vs `PSP` and `CONTROL` register | Determine if Unicorn models MSP and PSP as separate hardware registers. |
| CM-04: Hardware Exception Stacking | Trigger fault or exception entry | Observe whether Unicorn automatically pushes `{r0-r3, r12, lr, pc, xPSR}` onto the active stack. |
| CM-05: EXC_RETURN Semantics | Return via `BX LR` with `LR = 0xFFFFFFF9` / `0xFFFFFFFD` | Observe whether Unicorn natively decodes EXC_RETURN and unstacks registers. |
| CM-06: Peripheral & Interrupt Absence | Access SysTick or NVIC registers (`0xE000E010`, `0xE000E100`) | Document whether Unicorn provides built-in peripheral registers or treats them as unmapped memory. |

**Decision Gate:** The outcome of `P2-R` is purely informational. If Cortex-M requires writing custom exception stackers and NVIC emulators, it will be scheduled as a dedicated post-P2 profile milestone (e.g. Product P3) without gating P2 delivery.

## 4. Technical Architecture and Domain Changes

### 4.1 Dependency Addition
In Stage P2-A, `pyelftools` is added to `pyproject.toml` and pinned in `uv.lock`. Used strictly within `src/armstride/elf/`.

### 4.2 New Domain Records
- `Watchpoint(address: int, length: int, kind: str)`
- `WatchpointHit(watchpoint: Watchpoint, access_type: str, address: int, length: int, triggering_pc: int)`

- `SymbolTable(by_address: dict[int, list[SymbolEntry]], by_name: dict[str, SymbolEntry])`
- `LineTable(entries: list[LineEntry])`
- `ExecutionHistoryEntry(step_seq: int, registers: RegisterState, cpsr: int, mode: str, pc: int, modified_memory: dict[int, int], last_step: Optional[StepResult])`

- `POST /api/sessions/{id}/program` (multipart upload or base64 JSON for ELF)
- `GET /api/sessions/{id}/symbols`

- `POST /api/sessions/{id}/watchpoints`
- `DELETE /api/sessions/{id}/watchpoints/{address}`

`unsupported_elf_class`, `unsupported_elf_machine`, `unsupported_elf_type`, `elf_pie_unsupported`, `ambiguous_elf_execution_mode`, `elf_relocation_unsupported`, `elf_dynamic_linking_unsupported`, `elf_resource_limit_exceeded`, `invalid_watchpoint`, `history_empty`, `history_unavailable`.
