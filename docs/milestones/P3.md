# Product P3 Specification and Implementation Roadmap

**Status:** Proposed Architecture Specification & Feasibility Plan (P0, P1, and P2 baselines defined; P3 feasibility verified via spike; production implementation NOT yet started)  
**Document Version:** 1.0  
**Baseline:** Product P0, Product P1, and Product P2 Complete/Defined Baselines  
**Target Release:** ArmStride Product P3 ("RISC-V Introduction — RV32I")  

---

## 1. Executive Summary and Product Baseline

### 1.1 Multi-ISA Expansion Intent
Product P0 and Product P1 established ArmStride as a high-fidelity local snippet debugger for ARMv7-A / Thumb-2, providing atomic instruction stepping, exact partial memory tracking, runtime interworking, IT block handling, bounded Run, and breakpoints. Product P2 expanded the ARM debugger with direct ARM ELF32-LE loading, symbol navigation, DWARF source correlation, post-instruction memory watchpoints, and bounded linear Step Back.

**Product P3** defines the first multi-architecture expansion of ArmStride:
> **RISC-V Introduction — RV32I**

The objective is twofold:
1. Make ArmStride genuinely architecture-extensible rather than an ARM-only tool with bolted-on conditionals;
2. Provide a practical, high-clarity RISC-V learning and research environment for exploring instructions, registers, memory, and control flow without destabilizing existing ARM workflows.

ArmStride does not become a general OS emulator or full system simulator. It remains a focused, concrete fragment debugger:
```text
Paste assembly.
Inject state.
Step through it.
Inspect registers, memory, and branches.
```

### 1.2 Initial Product P3 Scope: RV32I
The initial P3 release target is strictly:
```text
RV32I (Base 32-bit Integer Instruction Set, Little-Endian)
```

Required P3 capabilities:
- **RV32I little-endian execution:** Full support for core RV32I computational, upper-immediate, memory transfer, branch, and jump instructions;
- **RISC-V assembly source input:** Textual assembly source with local labels, immediate offsets, and standard ABI aliases;
- **Addressed RISC-V disassembly/import input:** Parsing hex machine bytes and disassembly listings with machine bytes authoritative;
- **Concrete register editing:** Interactive editing of registers `x1`–`x31` and `pc`, with standard ABI aliases;
- **Strict `x0` immutability:** Register `x0` (`zero`) permanently wired to 0; user edits rejected with clear diagnostics; CPU writes produce no state changes or false deltas;
- **Strict `MemoryState` integration:** Reusing the proven partial-memory model (known instructions, stack, user data, unknown `??` bytes, patch, zero-fill);
- **Synthetic scratch stack:** Fixed stack allocation with `x2`/`sp` initialized to stack top;
- **Atomic single Step:** Transactional execution with exact snapshot rollback on memory/fetch faults;
- **Full Debugger Reuse:** Run / Stop, Breakpoints, Memory Watchpoints, Bounded Step Back (100 steps), Reset, and User Baseline State isolation reused across ISAs;
- **Profile-driven browser UI:** Svelte interface rendered dynamically from architecture profile metadata (no fake CPSR or N/Z/C/V flags on RISC-V);
- **Full ARM regression preservation:** Zero regression on existing ARMv7-A / Thumb-2 test baselines.

### 1.3 Explicit Non-Goals and Deferred Capabilities
The following capabilities are strictly excluded from initial Product P3 to maintain a sharp, deliverable boundary:
- **RV32M (Multiply/Divide):** Deferred to increment P3.1;
- **RV32C (Compressed 16-bit Instructions):** Deferred to increment P3.2 (requires mixed 16/32-bit instruction alignment handling);
- **RV64I (64-bit Base Integer):** Deferred to increment P3.3 (requires 64-bit XLEN, address space, and value representations);
- **RV32A / RV32F / RV32D:** Atomics and floating-point extensions deferred post-P3;
- **Vector / Bitmanip:** High-complexity extensions deferred post-P3;
- **Privileged Architecture:** Machine, Supervisor, and User privilege levels, MMU/page-tables, and virtual memory are excluded;
- **Platform Emulation & Devices:** No SBI (Supervisor Binary Interface), CLINT, PLIC, UART, timers, or MMIO peripheral emulation;
- **Arbitrary CSR Support:** CSR registers (`mstatus`, `mie`, `satp`, etc.) are not exposed;
- **Direct RISC-V ELF Loading:** Deferred to post-RV32I stage P3-H. Source and disassembly inputs are authoritative for initial bring-up;
- **System Emulation:** Operating system syscalls and runtime environments are not fabricated; `ECALL` and `EBREAK` behave as explicit debugger stop traps.

## 2. Why RV32I First

RV32I is selected as the initial architecture bring-up target based on technical invariants:
1. **XLEN Invariance (32-bit):** Matches ArmStride’s existing 32-bit address space (`1 << 32`), 32-bit unsigned register representations (`UInt32`), 32-bit memory indexing, and scratch stack infrastructure without pervasive type rewrites;
2. **Fixed Instruction Width (32-bit):** Every RV32I instruction is exactly 4 bytes aligned to 4-byte boundaries. This decouples the multi-ISA domain refactoring from variable-width instruction decoding and branch targets;
3. **Core RISC-V Execution Model:** Implements the complete fundamental RISC-V execution paradigm (load-store architecture, program counter advancement, register comparisons for conditional branches, separate link register jump mechanisms);
4. **Educational Value:** Provides the cleanest baseline for students, compiler engineers, and reverse engineers to learn RISC-V assembly without peripheral or compression noise;
5. **Verification Rigor:** Proves the multi-ISA domain boundary cleanly before expanding into multi-width (`RV32C`) or multi-XLEN (`RV64I`).

## 3. Feasibility Spike Findings (`spikes/p3_riscv/`)

A dedicated RISC-V semantics spike was defined and executed on the host runtime environment (`macOS arm64`, Python 3.14.7, Unicorn 2.1.4, Capstone 5.0.7). The spike script (`spikes/p3_riscv/probe.py`) verified 13 core areas and generated structured evidence in `spikes/p3_riscv/observations.json`.

### 3.1 Validated Instructions
The following instructions were proven under native Unicorn RV32 execution:
- **Arithmetic:** `ADD`, `ADDI`, `SUB`, `AND`, `OR`, `XOR`, `SLL`, `SRL`, `SRA`, `SLT`, `SLTU`
  - Signed overflow (`0x7FFFFFFF + 1 = 0x80000000`) and 32-bit unsigned wrapping (`0xFFFFFFFF + 1 = 0x0`) verified;
  - Immediate sign extension (`ADDI` with `-5` produces correct 32-bit signed adjustment);
  - Logical shift (`SRL`) zero-fills MSB; arithmetic shift (`SRA`) replicates sign bit (`0x80000010 >> 4` -> `0xF8000001`);
  - Signed comparison (`SLT` with `-1` and `1` yields 1); unsigned comparison (`SLTU` with `0xFFFFFFFF` and `1` yields 0).
- **Upper Immediate:** `LUI`, `AUIPC`
  - `LUI` sets upper 20 bits directly (`0x12345000`);
  - `AUIPC` calculates target from its own instruction address (`PC + (imm << 12) = 0x1004 + 0x1000 = 0x2004`).
- **Loads & Stores (Little-Endian):** `LB`, `LBU`, `LH`, `LHU`, `LW`, `SB`, `SH`, `SW`
  - Storing `0x12345678` at `0x2000` writes bytes `[0x78, 0x56, 0x34, 0x12]`, confirming native little-endian layout;
  - `LB` sign-extends byte `0x85` -> `0xFFFFFF85`; `LBU` zero-extends -> `0x00000085`;
  - `LH` sign-extends `0xFA85` -> `0xFFFFFA85`; `LHU` zero-extends -> `0x0000FA85`; `LW` reads full 32-bit word cleanly.
- **Branches:** `BEQ`, `BNE`, `BLT`, `BGE`, `BLTU`, `BGEU`
  - Branch taken updates PC to target (`PC + imm`); branch not taken advances sequentially (`PC + 4`);
  - Signed branch (`BLT` with `-5 < 2`) taken; unsigned branch (`BLTU` with `0xFFFFFFFB < 2`) falls through;
  - Branch-to-self (`BEQ zero, zero, 0`) holds PC at current instruction.
- **Jumps & Call/Return:** `JAL`, `JALR`
  - `JAL ra, +16` stores `PC + 4` in `ra` and jumps to target;
  - `JALR zero, ra, 0` returns to `ra` without modifying link register;
  - Target alignment: `JALR` clears bit 0 (`target & ~1`), masking unaligned target addresses automatically.

### 3.2 Critical Engine Insights and Behavioral Discoveries

| Probe Area | Observed Engine Behavior | Architectural Requirement / ArmStride Decision |
| :--- | :--- | :--- |
| **x0 Immutability** | Unicorn's `reg_write(UC_RISCV_REG_X0, val)` stores values into internal slot; `reg_read` returns that value! However, Unicorn's CPU execution (TCG) treats `x0` reads as constant 0 and discards instruction writes. | **ADR-027:** ArmStride domain MUST enforce x0 immutability. Reject user edits to `x0`/`zero` with HTTP 422 `x0_immutable`. Canonicalize `x0` to 0 on all state reads. Exclude `x0` from `StepResult` deltas. |
| **Data Alignment** | `LW` from unaligned address `0x2001` succeeded without native fault (returning `0x05040302`). Unicorn/QEMU defaults to emulating unaligned data accesses. | **ADR-030:** RV32I specification permits hardware misaligned data access or raising an address-misaligned exception. ArmStride will allow unaligned data accesses if within mapped memory, while rejecting accesses spanning into unmapped regions. |
| **Fetch Alignment** | Fetching from unaligned address `0x1002` (not 4-byte aligned in non-C RV32) raised native `UC_ERR_EXCEPTION`. | Fetch addresses must be 4-byte aligned in RV32I. Unaligned branch targets produce an execution stop `unaligned_pc`. |
| **Unmapped Fetch Fault** | Jumping to unmapped memory `0x9000` via `JAL ra, 0x8000` raised `UC_ERR_FETCH_UNMAPPED`. Inside Unicorn, `ra` was set to `0x1004` and `PC` to `0x9000` before fault. | ArmStride's transactional step model rolls back to the pre-step snapshot on any fault. A jump to unmapped memory rolls back completely, preserving pre-step PC and registers. |
| **Memory Hooks** | `UC_HOOK_MEM_READ` and `UC_HOOK_MEM_WRITE` fired with exact access sizes, addresses, and written values in strict program order. | Shared memory hook mechanics from ARM Unicorn backend are directly reusable. |
| **Step Count & Timeout** | `emu_start(..., count=1)` executes exactly 1 instruction and stops at next PC. Timeout halts infinite loops cleanly. | Single-step execution and bounded Run loops operate reliably on Unicorn RV32. |
| **Context Save / Restore** | `context_save()` and `context_restore()` successfully preserved and restored all 32 integer registers and PC. | Backend rollback and fast checkpointing function identically to ARM. |
| **System Instructions** | `FENCE` executes as NOP.<br/>`ECALL` raises `UC_ERR_EXCEPTION`.<br/>`EBREAK` raises `UC_ERR_INSN_INVALID`. | **ADR-032:** `ECALL` and `EBREAK` are recognized by ArmStride decoder/control-flow and reported as explicit debugger stop conditions (`environment_call`, `breakpoint_trap`) rather than unhandled engine errors. |

## 4. Multi-ISA Architecture Refactoring

ArmStride must transition from hard-coded ARM assumptions to an architecture-extensible model without over-engineering a complex plugin framework.

### 4.1 De-ARMing Shared Domain Contracts

The current codebase contains several ARM-specific concepts in shared contracts:
- `Mode = Literal["arm", "thumb"]`: Dynamic execution modes are unique to ARM. In RV32I, instruction execution mode is invariant (`riscv32` or None).
- `Instruction.profile = "armv7-a-le"` / `ProgramImage.profile = "armv7-a-le"`: Defaulted to ARM.
- `Breakpoint(address: int, mode: Mode)`: Couples breakpoints to ARM execution modes.
- `flags = nzcv` and `cpsr`: Exposed unconditionally on `StepResult`, `State`, and `views.py`.
- `ITContext`: Thumb-2 IT block metadata embedded in `StepResult`.
- `_it_blocks` parsing in `SimulationSession._replace`.

**Refactoring Plan (Stage P3-A):**
1. **Separate Profile Identity from Dynamic Execution Mode:**
   ```python
   # Architecture profile identifies the ISA and register set
   Profile = Literal["armv7-a-le", "rv32i-le"]
   
   # Execution mode is profile-dependent (None for RV32I)
   ArmMode = Literal["arm", "thumb"]
   ExecutionMode = Literal["arm", "thumb", "riscv32"]
   ```
2. **Profile-Driven Register Descriptors:**
   Introduce `ArchitectureProfile` contract defining:
   - Profile name (`armv7-a-le`, `rv32i-le`);
   - Canonical register names and aliases;
   - Initial register values and stack configuration;
   - Address alignment rules (2/4-byte for ARM, 4-byte for RV32I);
   - Status register definition (CPSR for ARM, None for RV32I);
   - Flag definitions (NZCV for ARM, empty for RV32I);
   - Register immutability rules (e.g. `x0` immutable).
3. **Decoupled StepResult / State:**
   - `cpsr_change`, `flag_changes`, and `it_context` become optional profile-specific fields;
   - For RV32I, `cpsr_change = None`, `flag_changes = {}`, and `it_context = None`;
   - Frontend renders the flags bar and CPSR editor only when `state.profile == 'armv7-a-le'` or when profile metadata specifies status flags.

### 4.2 Unified ProgramImage

`ProgramImage` remains the single executable-image abstraction across all architectures:
```text
ARM Assembly ───────┐
ARM Import ─────────┤
ARM ELF ────────────┤
                    ├───> ProgramImage ───> SimulationSession
RISC-V Assembly ────┤      (instructions,
RISC-V Import ──────┤       data_regions,
future RISC-V ELF ──┘       profile, mode)
```

- No `RiscvProgramImage` class.
- `ProgramImage.profile` explicitly stores `"rv32i-le"` or `"armv7-a-le"`.
- `Instruction` records maintain:
  - `address: int`
  - `raw_bytes: bytes`
  - `size: int` (always 4 for RV32I)
  - `display_text: str`
  - `decoded_text: str`
  - `decode: DecodeMetadata`
  - `profile: str`
  - `mode: ExecutionMode`

### 4.3 Architecture-Owned Control-Flow Boundary

Instead of expanding `control_flow.py` with multi-architecture `if/else` ladders, define an architecture-owned control-flow interpreter:
```python
class ControlFlowInterpreter(Protocol):
    def analyze(self, instruction: Instruction, registers: Mapping[str, int]) -> BranchAnalysis: ...
```

`BranchAnalysis` produces normalized domain outcomes:
```python
@dataclass(frozen=True)
class BranchAnalysis:
    is_control_flow: bool
    kind: Literal['branch', 'call', 'return', 'pc_write', 'trap'] | None
    condition_passed: bool | None
    taken: bool
    target: int | None
    fallthrough: int
```

- **ARM Interpreter:** Evaluates CPSR flags, IT block states, condition codes (`EQ`, `NE`, etc.), and branch/pop/ldm targets.
- **RISC-V Interpreter:**
  - Evaluates register comparisons directly (`rs1 == rs2` for `BEQ`, `rs1 < rs2` signed for `BLT`, etc.);
  - Computes direct branch targets: `target = instruction.address + immediate`;
  - Computes `JAL` targets (`PC + imm`) and identifies `call` convention when `rd == 'ra'`;
  - Computes `JALR` targets (`(registers[rs1] + imm) & ~1`) and identifies `return` convention when `rs1 == 'ra'` and `rd == 'zero'`;
  - Identifies `ECALL` and `EBREAK` as `trap` control-flow.

## 5. Register Model and x0 Semantics

### 5.1 Register Set
RV32I registers:
```text
x0, x1, x2, ..., x31, pc
```

### 5.2 ABI Alias Resolution
Standard ABI aliases are supported across all input and display paths:
```text
x0  = zero    x8  = s0/fp   x16 = a6    x24 = s8
x1  = ra      x9  = s1      x17 = a7    x25 = s9
x2  = sp      x10 = a0      x18 = s2    x26 = s10
x3  = gp      x11 = a1      x19 = s3    x27 = s11
x4  = tp      x12 = a2      x20 = s4    x28 = t3
x5  = t0      x13 = a3      x21 = s5    x29 = t4
x6  = t1      x14 = a4      x22 = s6    x30 = t5
x7  = t2      x15 = a5      x23 = s7    x31 = t6
```

- Canonical storage key in `MachineState.registers` is `x0` through `x31` plus `pc`.
- Aliases resolve to canonical names upon ingestion: `canonical_register("ra", profile="rv32i-le") -> "x1"`.
- Frontend displays both the ABI alias and canonical number (e.g. `x1 · ra`, `x2 · sp`).

### 5.3 x0 Immutability Rules (ADR-027)
1. **Initial State:** `x0` is initialized to `0` in `MachineState` and Unicorn backend.
2. **User Edits Rejected:** Any attempt to edit `x0` or `zero` via `POST /api/sessions/{id}/registers` is rejected immediately with HTTP 422 and diagnostic code `x0_immutable`.
3. **CPU Writes Suppressed:** Instructions writing to `x0` (e.g. `addi x0, x1, 10`) execute without error, but the architectural state of `x0` remains `0`.
4. **Delta Reporting:** `x0` is never included in `StepResult.register_changes`.
5. **Backend Ingestion:** Whenever register state is refreshed from the native engine, `x0` is explicitly set to `0`.

## 6. Execution Backend Architecture

The Unicorn execution adapter is structured via composition and clear inheritance:
```text
                BaseUnicornBackend (Abstract)
             ┌─────────────────┴─────────────────┐
             │                                   │
      ArmUnicornBackend                  RiscvUnicornBackend
   (ARMv7-A / Thumb-2,                 (RV32I, Little-Endian,
    Cortex-A15, CPSR,                   x0-x31 + PC,
    IT block handling)                  x0 immutability enforcement)
```

### 6.1 Shared Mechanics in `BaseUnicornBackend`
- Mapped page memory management (`PAGE_SIZE = 4096`);
- Backing page allocation and synchronization with `MemoryState`;
- Memory read/write hooks (`UC_HOOK_MEM_READ`, `UC_HOOK_MEM_WRITE`) and invalid memory access interception;
- Transactional checkpointing: `context_save()` and backing page memory hashing/snapshots;
- Atomic rollback: restoring memory bytes and `context_restore()` on fault;
- Deadlock and infinite loop timeout enforcement (`timeout_us = 1_000_000`).

### 6.2 Architecture-Specific Logic in `RiscvUnicornBackend`
- Initialized with `uc.Uc(uc.UC_ARCH_RISCV, uc.UC_MODE_RISCV32)`;
- Maps register IDs `UC_RISCV_REG_X0` through `UC_RISCV_REG_X31` and `UC_RISCV_REG_PC`;
- Enforces `x0 == 0` on initialization and post-execution readback;
- Validates 4-byte instruction fetch alignment;
- Detects `ECALL` and `EBREAK` exceptions and translates them to clean debugger stops;
- Decodes retired fetch destinations without ARM-specific mode shifts.

- The embedded RV32I assembler is verified against these oracle fixtures on every CI run.

- ARM `$a/$t/$d` mapping symbols are strictly excluded from the RISC-V parser.

## 8. RV32I Memory and Scratch Stack Semantics

### 8.1 Memory Semantics
- Strictly reuses existing `MemoryState` byte-level tracking:
  - `known`: Loaded instructions, data regions, initialized scratch stack, user memory patches;
  - `unknown`: All uninitialized address space represented as `??`;
  - Reads from unknown memory halt execution with `unmapped_memory_access` and roll back transaction;
  - Writes to unmapped memory allocate known pages and update `MemoryState`.

### 8.2 Scratch Stack
- Stack base placed at `0x200F0000`, size `0x10000` (64 KiB), matching ARM convention;
- Initialized as known zero-filled memory;
- Register `x2` (`sp`) initialized to `0x20100000` (stack top);
- ArmStride does not synthesize caller frames, argc/argv, or libc runtime data.

## 12. P3 Functional Requirements (P3-FR)

- **`P3-FR-001` (RV32I Execution):** The system shall execute little-endian RV32I instructions (`ADD`, `ADDI`, `SUB`, `AND`, `OR`, `XOR`, `SLL`, `SRL`, `SRA`, `SLT`, `SLTU`, `LUI`, `AUIPC`, `LB`, `LBU`, `LH`, `LHU`, `LW`, `SB`, `SH`, `SW`, `BEQ`, `BNE`, `BLT`, `BGE`, `BLTU`, `BGEU`, `JAL`, `JALR`, `FENCE`).
- **`P3-FR-002` (x0 Permanent Immutability):** Register `x0` (`zero`) shall always evaluate to `0`. Any user edit targeting `x0` shall be rejected with HTTP 422 `x0_immutable`. Instructions writing to `x0` shall execute normally without changing `x0` or reporting a delta.
- **`P3-FR-003` (RV32I Register Set & Aliases):** The register model shall expose `x0`–`x31` and `pc`, supporting all standard ABI aliases (`zero`, `ra`, `sp`, `gp`, `tp`, `t0`–`t6`, `s0`–`s11`, `a0`–`a7`).
- **`P3-FR-004` (Profile-Driven Domain Contract):** Architecture profile identity (`"armv7-a-le"`, `"rv32i-le"`) shall be separated from dynamic execution mode. No fake CPSR or NZCV flags shall be required or reported for RISC-V.
- **`P3-FR-005` (Unified ProgramImage):** `ProgramImage` shall accommodate RV32I instructions without creating an architecture-specific image subtype.
- **`P3-FR-006` (Architecture-Owned Control Flow):** Branch target and call/return analysis shall be performed by an architecture-owned interpreter producing normalized `BranchAnalysis` records.
- **`P3-FR-007` (Dedicated RISC-V Backend):** RISC-V execution shall be implemented in `RiscvUnicornBackend`, sharing generic page/memory/rollback helpers with ARM but keeping CPU setup and register IDs isolated.
- **`P3-FR-008` (RV32I Assembly Input):** The system shall assemble RV32I assembly source with local labels, numeric offsets, and ABI register aliases into authoritative machine bytes.
- **`P3-FR-009` (RV32I Disassembly Input):** The system shall parse addressed RV32 disassembly listings with machine bytes authoritative.
- **`P3-FR-010` (Encoding Oracle Verification):** RV32I test encodings shall be verified against an independent external assembler oracle (`llvm-mc` or GNU binutils).
- **`P3-FR-011` (Strict Memory Integration):** RV32I execution shall integrate with `MemoryState`, enforcing known/unknown byte bounds and snapshot rollback on unmapped accesses.
- **`P3-FR-012` (Synthetic Scratch Stack):** The session shall provide a 64 KiB scratch stack at `0x200F0000`, initializing `x2`/`sp` to stack top.
- **`P3-FR-013` (Debugger Feature Reuse):** Bounded Run, concurrent Stop, pre-execution Breakpoints, Memory Watchpoints, Bounded Step Back, and Reset shall function on RV32I sessions via shared session logic.
- **`P3-FR-014` (System Traps):** `ECALL` and `EBREAK` shall be reported as clean debugger trap stop conditions (`environment_call`, `breakpoint_trap`) rather than unhandled engine crashes.
- **`P3-FR-015` (Profile-Driven UI):** The frontend shall adapt its register grid, status indicators, and preset selections dynamically according to the loaded session profile.
- **`P3-FR-016` (ARM Regression Invariance):** All existing ARMv7-A / Thumb-2 capabilities and automated tests shall remain fully functional and passing.

## 13. P3 Acceptance Criteria Map (P3-AC)

| ID | Category | Requirement / Verification Target |
| :--- | :--- | :--- |
| `P3-AC-01` | Architecture Isolation | ARM regression suite remains 100% green with zero behavioral modifications to ARM execution. |
| `P3-AC-02` | Domain Boundaries | Shared domain contracts contain no hard-coded ARM conditionals for RISC-V operations. |
| `P3-AC-03` | x0 Immutability | Reading `x0`/`zero` always returns 0; user write attempt returns HTTP 422 `x0_immutable`. |
| `P3-AC-04` | x0 CPU Writes | Instruction `addi x0, x1, 5` executes cleanly, leaves `x0 == 0`, and reports no register change. |

| `P3-AC-13` | Conditional Branches | `BEQ`, `BNE`, `BLT`, `BGE`, `BLTU`, `BGEU` correctly branch when taken and fall through when not taken. |
| `P3-AC-14` | Jumps | `JAL` writes link address `PC + 4` to `rd` and updates PC; `JALR` masks bit 0 and jumps to target. |
| `P3-AC-15` | System Traps | `ECALL` and `EBREAK` stop execution cleanly with actionable stop reasons. |
| `P3-AC-16` | Assembly Input | RV32I source compiles to `ProgramImage` with accurate machine bytes and labels resolved. |
| `P3-AC-17` | Disassembly Input | Addressed hex text imports into `ProgramImage` with machine bytes authoritative. |

| `P3-AC-23` | Session Reset | Reset cleanly restores RV32I state from User Baseline State. |
| `P3-AC-24` | Profile-Driven UI | Frontend displays RV32I register grid, suppresses CPSR/flags, and supports stepping. |
